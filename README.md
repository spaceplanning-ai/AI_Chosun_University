# AI 남도 프리즘 — 프런트엔드

설명가능 AI 기반 광주·전남 초광역 관광 큐레이션 키오스크의 **프런트엔드 구현체**입니다.
제안서(`AI_남도프리즘_제안서_스페이스플래닝(주)_260804`)와 피드백 문서
(`0807_AI남도프리즘_단계별개발_회의_양미애 교수님 피드백`)의 A단계 필수범위를 기준으로 작성했습니다.

## 1. 저장소 구조 — 앱별로 분리 배포 가능

어드민과 서비스뷰를 서로 다른 저장소로 올릴 수 있도록, 배포 단위마다 폴더를 나누었습니다.

```
namdo-prism/
├── packages/
│   └── core/                     @namdo-prism/core — 공용 코어 (디자인 토큰·도메인·UI·로그)
├── apps/
│   ├── kiosk/                    서비스뷰 ① 전시장 세로형 터치 키오스크   (:3000)
│   ├── mobile/                   서비스뷰 ② QR 모바일 결과 페이지        (:3001)
│   └── admin/                    어드민 — 연구자 모드 및 검수 화면        (:3002)
└── package.json                  npm workspaces 루트
```

세 앱은 **서로를 import 하지 않습니다.** 공유하는 것은 `@namdo-prism/core` 하나뿐입니다.

### 왜 앱을 셋으로 나누었는가

배포 환경이 실제로 다르기 때문입니다.

| 앱 | 실행 환경 | 네트워크 | 접근 대상 |
| --- | --- | --- | --- |
| kiosk | 전시장 미니 PC (standalone 빌드) | **오프라인** | 관람객 |
| mobile | 공개 웹 호스팅 | 온라인 | 관람객 개인 단말 |
| admin | 내부망 / 접근 제한 | 온라인 | 교수·검수자·연구자 |

키오스크가 오프라인으로 구동되어야 한다는 요구(피드백 [기타] — 부트캠프에서는 오프라인 시연
모드만 구동)와, 어드민이 대중에게 노출되면 안 된다는 요구가 같은 배포 단위 안에서는 동시에
성립하지 않습니다.

### 별도 저장소로 분리하는 방법

각 앱 폴더는 `@namdo-prism/core` 하나만 외부 의존성으로 가집니다. 분리 시 앱의
`package.json` 에서 그 한 줄만 바꾸면 됩니다.

```jsonc
// 모노레포 (현재)
"@namdo-prism/core": "*"

// 별도 저장소로 분리한 뒤 — git 의존성
"@namdo-prism/core": "git+ssh://git@github.com/<org>/namdo-prism-core.git#v0.1.0"

// 또는 사내 레지스트리
"@namdo-prism/core": "^0.1.0"
```

`next.config.mjs` 의 `transpilePackages: ['@namdo-prism/core']` 는 그대로 두면 됩니다.
코어는 빌드 산출물이 아닌 소스(TypeScript)를 그대로 배포하며, Tailwind 스캔 경로도
`packages/core/src/styles/globals.css` 안의 `@source` 선언이 자기 위치 기준 상대경로로
잡고 있어 설치 위치가 바뀌어도 동작합니다.

## 2. 실행

```bash
npm install

npm run dev:kiosk     # http://localhost:3000  키오스크
npm run dev:mobile    # http://localhost:3001  QR 결과 페이지
npm run dev:admin     # http://localhost:3002  연구자·검수 화면

npm run build         # 세 앱 모두 프로덕션 빌드
npm run typecheck     # 전체 타입 검사
npm run lint
npm test              # 도메인 · 대비 · 색 구분 · 도면 · 지도 · XLSX 회귀 테스트 (174건)
npm run contrast      # 색 대비 WCAG 검사 보고서
```

### 데이터·문서 생성 명령

```bash
npm run data:export       # 관광지·공식문서를 CSV로 내보내기 (엑셀 편집용)
npm run data:import       # 편집한 CSV를 JSON으로 반영 (검증 실패 시 기록하지 않음)
npm run data:validate     # 무결성 검사만 수행

npm run patent:examples   # 특허 기술설명서 + 도면 + 예시 입출력 자동 생성
npm run package:kiosk     # 전시장 배포 꾸러미 생성 (dist/kiosk)
```

### 전시장 배포

```bash
npm run package:kiosk
```

`dist/kiosk/` 폴더를 통째로 전시 PC에 복사하고 `키오스크_실행.bat` 을 실행하면 끝납니다.

> Next 의 `output: 'standalone'` 은 **정적 자산(`.next/static`)을 일부러 빼 놓습니다** — 보통 CDN이
> 맡기 때문입니다. 전시장에는 CDN이 없으므로 그대로 복사하면 서버는 뜨는데 CSS·JS가 전부 404가
> 나서 글자만 남은 화면이 대형 모니터에 걸립니다. 빌드도 성공하고 서버 로그도 깨끗해 현장에서
> 원인을 찾기 어렵습니다. 이 스크립트가 빠진 자산을 채우고 실행 스크립트까지 붙입니다.
> 꾸러미를 실제로 띄워 CSS·JS가 200으로 응답하는 것까지 확인했습니다.

전시 담당자용 절차서는 **`docs/운영매뉴얼.md`** 입니다 — 설치·당일 점검·시연 요령·장애 대응·종료 절차를
개발 지식 없이 따라갈 수 있게 정리했습니다.

키오스크의 QR이 가리킬 모바일 주소는 환경변수로 주입합니다.
전시장에서는 미니 PC의 로컬 IP를 넣으면 그대로 동작합니다.

```bash
# apps/kiosk/.env.local
NEXT_PUBLIC_MOBILE_BASE_URL=http://192.168.0.20:3001
```

## 3. 디자인 토큰 — 3계층 구조

색·크기 값을 컴포넌트에 직접 쓰지 않습니다. 세 계층을 거칩니다.

```
Layer 1  tokens.primitive.css   원시 팔레트·스케일        (--np-teal-500, --np-size-body …)
Layer 2  tokens.semantic.css    역할 토큰                 (--brand-solid, --font-body …)
Layer 3  theme.css              Tailwind 네임스페이스 매핑 (bg-brand, text-body …)
```

**핵심은 `<html>` 의 data 속성 네 개가 Layer 2만 갈아 끼운다는 점입니다.**

| 속성 | 값 | 효과 |
| --- | --- | --- |
| `data-ui-mode` | `standard` \| `large` | 일반 / 큰 글씨·큰 버튼 모드 (RFP 접근성 요구) |
| `data-theme` | `light` \| `exhibition` | 밝은 미색 / 어두운 전시용 배경 |
| `data-contrast` | `normal` \| `high` | 고대비 테마 (C안 범위) |
| `data-surface` | `kiosk` \| `mobile` | 세로형 키오스크 / 모바일 밀도 |

Tailwind 유틸리티가 값이 아닌 **변수를 참조**하도록(`@theme inline`) 구성했기 때문에,
`data-ui-mode="large"` 하나만 바뀌면 글자·여백·터치 타깃·테두리 두께가 전 화면에서 함께
커집니다. 컴포넌트에는 모드 분기 코드가 한 줄도 없습니다.

```css
.p-xl          { padding: var(--gap-xl) }
.text-display  { font-size: var(--font-display) }
.h-control-md  { height: var(--control-md) }
```

## 4. 특허 후보 모듈 분리

피드백 5.3의 "두 기술이 구분 가능한 모듈·로그·도면으로 남도록" 요청에 따라
디렉터리 단위로 분리했습니다. 어드민의 **특허 모듈 맵** 탭에서 같은 표를 화면으로 확인할 수 있습니다.

```
packages/core/src/domain/
├── linkage-recommendation/     특허 후보 제1안
│   ├── conditionVector.ts        3) 여행조건 → 평가요소 벡터
│   ├── retrieval.ts              4) 공식문서 검색
│   ├── trust.ts, eligibility.ts  5) 정보 신뢰도 · 후보 제외
│   ├── linkageIndex.ts           6) 초광역 관광연계지수
│   ├── scoring.ts, composer.ts   7) 다목적 추천점수 · 일정 생성
│   └── rationale.ts              8) 추천 이유 · 근거문서
│
├── minimal-change-replan/      특허 후보 제2안
│   ├── constraintChange.ts       제약조건 변화 비교
│   ├── impact.ts                 변경 대상 식별
│   ├── replacementSearch.ts      대체 후보 탐색 · 적합성 평가
│   ├── minimalChange.ts          최소변경 재구성
│   └── changeDiff.ts             변경 전/후 차이 계산
│
└── shared/                     두 발명 어디에도 속하지 않는 공통 기반
    ├── scheduling.ts             이동시간 산정 · 시각 재계산
    ├── metrics.ts                일정 지표
    └── acceptance.ts             검수 게이트 자동 판정
```

**의존 방향은 제2안 → 제1안 한 방향뿐입니다.** 제1안은 제2안을 참조하지 않으므로
제2안 폴더를 통째로 들어내도 제1안은 그대로 컴파일되고 동작합니다. 두 발명을 각각 별도
권리화 검토할 수 있게 하는 근거가 이 방향성입니다.

로그 역시 제2안의 산출값이 `refinements[]` 아래에만 모여 있어, CSV 단계에서 두 발명의
실시예 데이터를 분리해 추출할 수 있습니다.

### 기본값과 응답의 분리 (연구 로그 오염 방지)

추천 엔진은 **완전한 여행조건**을 입력으로 받아야 하므로 `DEFAULT_CONDITIONS` 가 미리 채워집니다.
그런데 그 상태를 화면에서 「선택됨」으로 보여 주면, 아무것도 누르지 않은 관람객이
**연인·1박2일·대중교통을 골랐다고 기록**됩니다. 제안서 10.4 로그의 `conditions` 가 그대로
논문의 독립변수가 되므로, 이 오염은 분석 결과를 바꿉니다.

그래서 키오스크 세션에 `answeredFields` 를 두어 **«값이 채워져 있음»과 «관람객이 답했음»을
분리**했습니다.

- 누르기 전에는 어떤 선택지도 선택 상태로 보이지 않습니다.
- 「다음」은 그 단계를 실제로 답해야 열립니다 (복수선택 단계는 원래 그랬고, 단일선택 단계도 이제 같습니다).
- 진행자 패널의 시연 시나리오는 의도적으로 고른 값이므로 전 항목을 답한 것으로 봅니다.

### 데이터 교체 (피드백 3.2)

관광지·공식문서의 원본은 `packages/core/src/data/*.json` 이며, TypeScript 파일은 로더일 뿐입니다.
엑셀로 편집한 뒤 되돌리는 절차 전문은 **`packages/core/src/data/README.md`** 에 있습니다.

- `data:import` 는 **검증을 통과하지 못하면 아무것도 쓰지 않습니다.** 깨진 JSON을 남겨
  앱이 아예 뜨지 않는 상황을 만들지 않기 위한 것입니다.
- 검색 색인은 **별도 갱신 명령이 필요 없습니다.** 앱 시작 시 JSON에서 다시 만들어지며,
  문서 키워드에 관광지 이름·소재지·지역명이 자동으로 파생 결합됩니다.
- 개발 모드에서는 앱 로드 시점에도 같은 검증이 돌아, 잘못된 데이터가 화면까지 흘러가지 않습니다.

도면도 그림 파일로 관리하지 않고 코드에서 생성합니다. 임계값·가중치가 설정 상수에서 오므로
구현을 고치면 도면의 숫자도 함께 바뀝니다. 어드민 「특허 모듈 맵」 탭에서 바로 볼 수 있습니다.

문서의 **모든 수치·임계값·가중치는 실제 구현을 실행해 얻은 값**입니다. 손으로 옮겨 적지 않으므로
구현이 바뀌면 문서도 함께 바뀝니다 — 기술설명서와 코드가 어긋난 채 출원되는 사고를 막는 구조입니다.

### 비교 테스트 모드 (피드백 7.1 — "가능 여부 별도 회신" 항목)

**회신: 구현 가능하며 이미 포함했습니다.** 어드민 「비교 테스트」 탭에서 실행합니다.

같은 여행조건을 제안 알고리즘과 대조군 2종에 각각 통과시켜 결과 품질을 대조합니다.
특허의 진보성 주장과 논문의 비교 자극물이 같은 실행에서 나옵니다.

| 대조군 | 모사 대상 |
| --- | --- |
| 인기·접근성 순 목록형 | 일반 관광안내 키오스크 — 목록·지도를 주고 선택은 이용자에게 맡기는 방식 |
| 취향 매칭 단일점수형 | 생성형 AI를 단순 연결한 방식 — 취향은 맞지만 근거·이동 실현성을 확인하지 않음 |

시나리오 4종 평균, 제안 방식이 대조군 평균 대비:

| 비교 항목 | 차이 |
| --- | --- |
| 초광역 연계지수 | **+19.1점** |
| 회피한 운영시간 위반 | **3.4곳** |
| 회피한 보행조건 위반 | **2곳** |
| 근거 제시율 | **100% 대 0%** |

> 대조군은 외부 벤치마크가 아니라 **본 저장소가 정의한 구현**입니다. 통상적인 관광안내
> 서비스의 동작을 모사한 것이며 특정 상용 제품과의 성능 비교가 아닙니다. 선정 규칙 전문은
> 화면과 `domain/shared/comparison.ts` 에 공개되어 있으니, 정의의 타당성을 먼저 검토한 뒤
> 결과를 해석해 주십시오.

### 연구로그 내보내기 (피드백 7.1)

| 형식 | 용도 |
| --- | --- |
| CSV 5종 | 통계 도구 반입. `session_id` 로 조인 |
| **XLSX 워크북** | 같은 내용을 한 파일의 다섯 시트로. **숫자를 숫자 형식으로 저장**해 바로 집계 가능 |
| JSON 원본 | 키오스크 → 어드민 전달. CSV로 표현이 어려운 중첩 구조까지 보존 |

XLSX는 외부 라이브러리 없이 작성합니다. 키오스크는 오프라인 구동이라 번들 크기가 부팅 시간에
직결되는데, 필요한 기능은 "문자열과 숫자로 된 표 다섯 장"이 전부이기 때문입니다.
무압축 ZIP + 최소 OOXML 로 구성했고, **openpyxl(제3자 리더)로 열어 시트·값·타입을 확인**했습니다.

### 지역 구분색 (색만으로 정보를 전달하는 자리)

지도 노드처럼 **지역명이 적히지 않는 자리**에서는 색이 유일한 단서입니다.
원래 광주=청록 / 전남=녹색이었는데, 두 색의 거리가 정상 시각 기준 **ΔE 5.5**(기준 15)로
사실상 구분되지 않았습니다. 대비율 검사로는 잡히지 않는 결함입니다 — 밝기가 비슷하면
대비율은 1에 가깝게 나오고, 그건 "문제없음"이 아니라 "구분 불가"를 뜻합니다.

제안서 11.2의 보조색상(녹색·하늘색)을 그대로 쓰되 하늘색을 광주에 배정해 **ΔE 18.0** 을 확보했습니다.

| 역할 | 이유 |
| --- | --- |
| `--region-*` | 뱃지·글자용. 옅은 배경 위 4.5:1 이 필요해 어둡다 |
| `--region-*-mark` | 지도·차트 마크용. 도형으로 구분되어야 해 밝고 채도가 높다 |

같은 색상 계열이라 정체성은 유지되며, 두 역할 모두 테스트가 거리를 지킵니다.

### 색 대비 검증 (접근성)

「큰 글씨 모드」를 A안에 포함해 달라는 요청의 근거는 **디지털 평등/접근성**이었습니다.
글자만 키우고 대비를 확인하지 않으면 그 근거의 절반만 충족하는 셈이므로, 팔레트를
눈으로 고르지 않고 **WCAG 대비율로 측정**했습니다.

```bash
npm run contrast
```

밝은/전시 × 일반/고대비 **4개 조합 × 26개 글자·배경 쌍 = 104건**을 브라우저 없이 검사합니다.
`color-mix(in oklab, …)` 로 정의된 전시 테마의 옅은 배경까지 직접 계산하므로 검사 누락이 없습니다.

측정 결과 **밝은 테마의 옅은 뱃지 8종이 기준 미달**이었고(주의 뱃지 2.57:1, 강조색 글자 2.83:1 등),
역할색을 어두운 단계로 내리고 채움 위 글자를 흰색으로 바꿔 해결했습니다.
전시 테마는 반대로 밝은 단계가 필요해 브랜드색을 한 단계 밝혔습니다.
현재 **104건 전부 통과**하며, 회귀는 테스트가 막습니다.

### 화면 캡처 검수 (`npm run shots`)

대비검사는 **토큰 값**을 재고, 이 스크립트는 **실제로 그려진 화면**을 봅니다. 둘은 다릅니다.

```bash
npm run dev:kiosk   # 세 앱을 각각 띄운 뒤
npm run shots       # docs/screenshots/ 에 화면을 캡처
# 포트가 겹치면: KIOSK_URL=http://localhost:4300 ADMIN_URL=http://localhost:4302 npm run shots
```

설치된 Chrome 을 헤드리스로 띄우고 Node 내장 WebSocket 으로 DevTools 프로토콜에 직접
말하므로 **브라우저 자동화 라이브러리를 추가하지 않습니다.**

이 방법으로 실제로 잡은 결함입니다. 전부 타입검사·린트·테스트·빌드·대비검사를 통과하던 것들입니다.

| 결함 | 왜 다른 검사로 안 잡혔는가 |
| --- | --- |
| 대기화면 배경 아트가 한 픽셀도 안 그려짐 (`-z-10` 이 body 배경 아래로 내려감) | DOM 에는 정상적으로 존재한다 |
| `animate-fade-in`(`fill-mode: both`)의 끝 키프레임이 `opacity` 지정을 덮어씀 | 애니메이션 값이 선언값을 이기는 것은 CSS 규칙대로다 |
| 한국어가 어절 중간에서 갈라짐 (「이야기」→ "이 / 야기") | 문자열은 올바르고, 줄바꿈은 브라우저가 정한다 |
| 이미지 여행카드도 같은 증상 (캔버스는 CSS 가 닿지 않음) | 캔버스 픽셀은 DOM 검사 대상이 아니다 |
| 제목의 조사 겹침·비문 ("광주의 남도의 맛", "연인 떠나는") | 문자열 연결은 타입이 맞다 |
| 밝은 테마 보조글자가 아이보리 배경에서 3:1 미달 | 대비검사가 그 조합을 검사하지 않았다 (지금은 추가) |
| 큰 글씨 모드에서 지표 라벨이 말줄임으로 잘림 (「평균 정보 신뢰…」) | 일반 모드에서는 폭이 충분해 드러나지 않는다 |
| 가까운 방문지의 지도 노드가 겹쳐 순번 숫자가 가려짐 | 좌표 계산은 정확하다. 겹침은 그림에서만 보인다 |
| 관문 이름표가 방문지 노드에 가려짐 | 겹침을 푼 뒤에야 생긴 2차 충돌이다 |
| 여행조건 1·2·4단계가 기본값으로 미리 선택돼 있음 | 값이 채워져 있는 것과 관람객이 답한 것을 코드가 구분하지 않았다 |
| 연구자 화면 하이드레이션 불일치 (서버가 잰 응답시간이 HTML 에 박힘) | 화면은 정상으로 보이고 콘솔에만 오류가 남는다 |

캡처 결과물은 저장소에 담지 않습니다(실행할 때마다 새로 만듭니다).

### 테스트 (검수 재현성)

```bash
npm test    # 174건
```

별도 테스트 프레임워크나 네이티브 바이너리에 의존하지 않습니다(Node 내장 러너).
인계받은 쪽에서 `npm install` 만으로 검수를 재현할 수 있습니다. 고정하는 불변식:

- 같은 입력 + 같은 기준일 → 항상 같은 일정 (재현성)
- 모든 방문이 운영시간 안에서 끝나고, 하루 활동 가능시간을 넘지 않음
- 제외된 관광지가 일정에 등장하지 않고, 모든 제외에 사유·단계·수치가 붙음
- 한 지역만으로 구성된 일정은 연계지수 구성요소가 0이 되고, 두 지역이 섞였다고 자동 만점이 되지 않음
- 재구성은 최대 2곳만 교체하고, 원본 일정을 변형하지 않으며, 교체 후에도 일정이 성립함
- 목표 달성으로 표시했다면 지표가 실제로 그 방향으로 움직였음
- 대조군이 제안 방식의 검증 로직을 물려받지 않아 비교가 성립함
- 4개 표시 조합 전체에서 글자·배경 대비가 WCAG AA를 충족함
- 특허 도면의 박스가 겹치지 않고 화면 밖으로 나가지 않음
- XLSX 워크북이 엑셀 필수 파트를 갖추고 숫자를 숫자 형식으로 저장함
- 색만으로 구분하는 지역 마크가 ΔE 15 이상 떨어져 있음
- 시험결과서 문서의 판정·수치가 검수 게이트 화면의 값과 어긋나지 않음
- 설문으로만 얻을 수 있는 연구변수에 로그 필드가 붙어 있지 않음
- 일정 제목에 조사가 겹치지 않고, 동행 표현이 「떠나는」 앞에서 부사구로 성립함
- 이미지 여행카드의 줄바꿈이 어절을 쪼개지 않음
- 지도 노드가 서로 겹치지 않고 화면 안에 남으며, 같은 일정은 항상 같은 그림이 됨
- 관문 이름표가 방문지 노드에 가려지지 않음

### 검수 게이트 (피드백 4장) 실측치

### 논문 연구모형 ↔ 로그 필드 (제안서 10.3 / 10.4)

어드민 **연구모형** 탭에서 확인합니다. 제안서 10.3의 변수 14개마다
**무엇으로 측정하는지**를 세 갈래로 명시했습니다 (`data/researchModel.ts`).

| 측정 수단 | 개수 | 의미 |
| --- | --- | --- |
| 로그로 측정 | 8 | 해당 로그 필드명을 함께 표시 (예: 개인화 정도 → `candidates[].criteria.preferenceFit`) |
| 설문 필요 | 5 | 인지된 신뢰도·적합성·설명 이해도·만족도·방문의도 — 시스템이 만들어 낼 수 없는 값 |
| 측정 불가 | 1 | 키오스크/모바일 이용환경 — 오프라인 구동이라 QR 접속 여부를 키오스크가 알 수 없음 |

설문값에 비슷한 이름의 로그 필드를 만들어 두면 **측정하지 않은 값을 측정한 것처럼**
논문에 쓰게 됩니다. 그래서 타입(`MeasurementSource`)으로 아예 붙일 수 없게 했고,
측정 불가 항목도 숨기지 않고 사유와 함께 화면에 남깁니다 —
전시가 끝난 뒤에 "그 변수를 재려면 이 값이 필요했는데 안 남겼다"를 알게 되는 일을 막습니다.

## 6. 구현 범위에 대한 명시

프런트엔드만 구현한 저장소입니다. 다음은 **의도적으로 포함하지 않았습니다.**

- **임베딩 / Vector DB 검색** — 백엔드 범위입니다.
  현재 `retrieval.ts` 는 오프라인 시연용 **어휘 기반 검색기**이며, 반환 타입·점수 의미(0–1)·
  로그 필드를 백엔드 검색기와 동일하게 맞추어 두었습니다. 백엔드 연결 시 이 파일 하나만
  교체하면 화면·로그·검수 지표는 그대로 유지됩니다.
- **LLM 호출** — 추천 이유 문장은 생성모델이 아니라 점수 계산에서 파생됩니다.
  화면의 설명과 실제 계산이 어긋날 수 없게 하기 위한 선택이며, 이 구조 자체가
  설명가능성의 근거입니다.
- **실시간 길찾기 / 날씨 / 예약·결제** — 제안서 12.4의 MVP 제외 권고 항목입니다.
  이동시간은 좌표 기반 거리 추정(`shared/scheduling.ts`)으로 일정 실현 가능성만 판단합니다.

## 7. 개인정보

이름·연락처·영상·정확한 위치를 수집하는 코드는 존재하지 않습니다.
세션 식별자는 매 세션 새로 생성되는 난수이며 어떤 개인 식별자와도 연결되지 않습니다.
QR에는 관광지 id 와 시각만 담기고 서버 왕복이 없습니다.
로그 스키마에 필드를 추가할 때는 `logging/schema.ts` 상단의 개인정보 원칙을 먼저 확인하십시오.
